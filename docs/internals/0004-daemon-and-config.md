# 0004: The daemon, config and transports

Status: Phase 2, 2026-11-16. How `pulse-daemon` and `pulse-cli` implement [0002](0002-architecture.md), and where they differ from it. Each point says why.

## Engine

- **One task owns routing state.** The engine task holds `RouterState`, the dedupe table and the recent-runs list; nothing else touches them, so there are no locks around routing. It has two inputs: a control channel (config, snooze, pause, run started/ended, "recount backlogs", "copy the state for a dry run") and an event channel (sources, ingest, report, replay). Control is handled first (`biased`), so a run is known to attribution before its first file event is routed.
- **Batches.** After one event it drains up to 255 more that are already waiting, routes them all, and commits events, deliveries, runs, outbox rows and rule state in **one** `Store::commit`. Callers (ingest, report, replay) are answered after the commit, so an accepted id survives a crash of the daemon process. It does not always survive an OS crash or power loss: the store runs SQLite in WAL mode with `synchronous=NORMAL`, which syncs the WAL at checkpoints, not at every commit, so the last commits before such a crash can be lost; the database is never corrupted, and what is lost is the newest commits, whole (a commit is all there or not at all). A sender that must not lose an event across power loss keeps it until it sees it in the log (`events.query`), or resends with a `dedupe_key`. `synchronous=FULL` would close this at the cost of an fsync per commit, which is the wrong cost for a daemon that runs all day and should be invisible.
- **A failed commit leaves nothing**, in the log or in memory. `route()` had already counted fires, armed debounces, tripped breakers and raised backlogs for events that were never stored; the engine keeps a copy of the routing state from before the batch and goes back to it. (It used to rebuild the state from the log, which also dropped debounces pending from earlier batches.) The dedupe table is refilled from the log, because `accept` had marked the batch's keys as seen and the sender's correct retry was dropped as a duplicate (found in review). Ids skipped by the failed batch are not reused, which the log allows (ids only have to increase); nothing was published and the worker was not woken. Debounces that had elapsed in a failed batch are lost, not retried at once against a store that is failing. Tested with an injected SQLite trigger.
- **Changing `dedupe_ttl` or `dedupe_capacity`** builds a new table and refills it from the log, as at startup; it used to start empty, so every key accepted within the TTL could be accepted again.
- **One timer**, armed after every step for `RouterState::next_deadline()`.
- **Dedupe keys are per source** (`<source uri>\0<key>`): two sources may use the same key for different things.
- **Exact causation outlives the run.** `PULSE_RUN_ID` on a reported event is resolved from memory, else from the store, so `pulse run` inside a run that has just ended still attributes exactly. Reported and inferred causation only use runs that are active or within `causation_grace`.
- **What survives a restart** (added with the end-to-end tests, 0009). The dedupe table is refilled from the log (keys accepted within `dedupe_ttl`), so an external source retrying after an outage does not fire twice. The runs inference needs are reloaded (ended within `causation_grace`), as opaque: their output is no longer read, so their writes are inferred, not reported; a run that was still `running` when the daemon died counts as active until its timeout would have ended it, because its agent is in its own process group, survived the crash, and nothing enforces the timeout any more. Without this, an orphaned agent's writes after a crash re-fired its own rule.
- **Backlogs** (`queued + running` per agent) are recounted from the store whenever run states change outside routing (approve, cancel, end, rerun). Routing increments them itself for the fires it makes.

## Effect worker

- **A run starts as of just before its spawn** (`started_at`). It was recorded after the supervisor's `Started`, and an agent that wrote a file at once could do it "before its run started", escaping inferred causation (seen under load, 8 ms).
- Claimed `start_run` rows wait in a FIFO per agent and start while the agent is under `max_concurrent` (read from the current config, else the run's snapshot). A row stays `claimed` until its run starts, so a crash returns it to pending. The run is re-read before it starts; one cancelled while it waited is skipped.
- **Global pause also holds queued runs.** 0002 says "nothing fires". A user who pauses because an agent misbehaves also expects runs already queued not to start; they start on resume. Running runs continue; cancel them explicitly.
- **Default working directory is per run**: `$PULSE_HOME/runs/<run id>/`, which also holds `event.json` (`PULSE_EVENT_FILE`). 0002 said `runs/`; a shared directory would let one run's files be attributed to another and would mix their outputs. Retention removes the directories of pruned runs.
- **Only the prompt text is stored** (`runs.prompt`), so a run started later gets a `RenderedPrompt` with the stored text and an empty `delimiter` field. The text already contains the fenced event block and its delimiter lines, and adapters send exactly the text, so what is stored is what the agent read (tested with `fake-claude` and `fake-codex` saving their stdin). The empty field is metadata nobody reads.
- **Graceful shutdown records `interrupted`** (with "the daemon shut down"): every run is cancelled through its token, the supervisor terminates its group, and the worker waits for each to be reaped. This needed `running → interrupted` in `RunTransition::Finish`; before, interrupted was only written at the next start, with the wrong end time. A crash is still recovered at the next start.
- A cancelled run is `cancelled`; one cancelled because of shutdown is `interrupted`.
- **Reruns skip routing**: they are an explicit request with the daemon token, so no approval, cooldown or rate limit applies. The run keeps its rule only while that rule still exists.

## Fan-out

- The engine publishes each committed batch once to a bounded `broadcast` (256 batches) and never waits. Each subscription is a task that filters into a buffer of the **200 newest** matching items and delivers at most **one batch per 250 ms** with a `dropped` count; the first batch after a quiet period goes out immediately. If the client's queue is full the buffer keeps summarizing; a client stuck for 30 s is disconnected. An idle subscription has no timer.
- A subscriber that falls behind the broadcast itself loses whole batches; those are counted in `dropped` by **batch**, not by matching event (which is unknown). `dropped > 0` means "the live view is incomplete; query the log", not an exact count.
- `runs.changed` keeps the **latest state per run** within a window: a run that went `queued → running → succeeded` in 250 ms is reported once, as `succeeded`. Views show state, not transitions; transitions are in the run itself.
- **Run output is pulled, not pushed.** An output subscription keeps a cursor and reads pages from the store when the run's `watch` counter moves (at most every 100 ms). A slow client reads bigger pages later; nothing is buffered for it and nothing is lost.
- `state.changed` is coalesced (100 ms) and carries the full status. It is also sent, with no topics, when only run counts changed (and the status really differs from the last one sent), so a client that shows "2 waiting for approval" (the desktop shell's badge) needs no run subscription. Before the web UI was wired to the daemon it was sent only for topic changes and the counts in it went stale.
- **Outcomes travel with events** to clients holding the daemon token: `events.batch` is `EventsBatchWithOutcomes` and `events.query` returns `EventPageWithOutcomes`, each with a compact `EventOutcome` (rule, delivery outcome, run) per delivery of its events. The engine publishes each commit's deliveries with its events, and deliveries recorded later for an earlier event (a debounce elapsing) with that event marked as not new, so subscribers send only the outcome. Agents over MCP get wakeups (for new events only) and scoped `EventPage`s: they are not told what other rules decided. Without this the UI asked `events.get` per visible row to show loop blocks, which does not survive a storm.
- **A subscribe call is answered before its first notification.** Each RPC subscription starts gated; the connection opens the gate once the response is queued (the queue is FIFO). Without it, output that was already stored could overtake the response.
- Live filters are evaluated by `pulse_core::filter::CompiledFilter`, which follows the store's query semantics so a subscription and a query agree.

## Config

- **Warnings** (added with 0009). Config that loads but cannot work: a rule whose `on` matches no type, whose `where` names a field no matching event has (or a relative glob on a path field, which never matches an absolute path), or whose agent's scopes cannot cover its events (every delivery would be `permission_denied`); an agent used by a rule whose program is not installed or whose `cwd` does not exist. The rule checks are `pulse_core::lint`; the filesystem checks are the daemon's and are re-done on every `system.status` / `system.config_errors`, so creating the directory clears the warning. Reported in `system.config_errors.warnings` and `SystemStatus.config_warnings`, logged when they change, and printed by `pulse start` and `pulse status`. Config errors are logged too: a headless daemon's log is where a broken file is noticed.
- **Last good, per file.** If `pulse.toml` stops parsing, its last good version stays in effect and the errors (file, line, item, field) are in `system.config_errors` and `pulse status`. If the files parse but do not resolve together (a rule names a missing agent), the whole previous config stays. A project file has **no** last good: content that does not match its trusted hash is inert.
- **Write-back** (`rules.upsert`, `set_enabled`, `archive`, `agents.upsert`, `sources.delete`, …) edits the owning file with `toml_edit`, checks the result exactly as a reload would (parse, resolve with the other files, compile routing), writes a temp file and renames it, then reloads. Invalid definitions are refused with the errors and the file is not touched.
  - Old and new are compared **by meaning**, through the typed definition: `on = "x"` and `on = ["x"]` are equal, so writing back an unchanged rule changes no byte. Only keys whose meaning changed are rewritten; a rewritten value keeps its key's comments and its trailing comment. A key changed back to its default is removed unless a comment is attached to it, so `disable` then `enable` restores the file byte for byte.
  - New definitions are appended without keys that only restate defaults.
  - **A `pulse.toml` that is a symbolic link** (into a dotfiles repository) stays one: the temp file is written next to the file the link points to and renamed over that file. Renaming over the link replaced it with a regular file, and later edits to the linked copy were silently ignored (found in review). The same holds for a project's `pulse.toml`; its trust already covered the content read through the link, which is the content written.
- **Trust** records (`name, dir, sha256, trusted_at`) live in the `kv` table under `trusted_projects` as JSON, so no migration was needed. Write-back to a project file re-binds the trust to the new hash: the user made the change with the daemon token. Any other change makes the project inert until `pulse project trust` again. Trusting requires the file to parse; names default to the directory name and must be valid names.
- **Watching**: the directories holding config files are watched (editors replace files by renaming), only for content changes to `pulse.toml` — not for access events: reading the file during a reload produces one, which in the first manual run caused a reload every ~150 ms. Changes settle for 150 ms before a reload. SIGHUP also reloads. A `pulse.toml` that is a symbolic link is followed: the directory of its target is watched too, and links are resolved again at every reload, so re-pointing one takes effect after the reload the link change itself causes.
- Not hot-reloaded: `[daemon] port` (takes effect on restart; logged), `log_level`, and `debounce_capacity` (the debouncer is sized at start).

## Transports and auth

- One listener on `127.0.0.1`: `/ws`, `POST /ingest?source=<name>`, `GET /auth/proof`, `POST /auth/login`, `/mcp`, and the UI. A guard runs first on every request: `Host` must be `127.0.0.1:<port>` or `localhost:<port>`; a present `Origin` must be this daemon's; `/ws` and `/ingest` need the daemon token; on `/mcp` no `Origin` is accepted at all, and the token is left to the MCP router's own bearer layer, which is the one place that decides the calling agent (`Services::mcp_agent`); the daemon token is not an agent token, so it gets 401 there.
- **Browsers** cannot set headers on a WebSocket, so the token may also come as the subprotocol `pulse.token.<token>`, offered together with `pulse` (which the server selects). Cookies were rejected: they are not port-scoped, so another server on 127.0.0.1 would receive them.
- **A browser cannot read the status of a refused upgrade**: a 401 and a daemon that is down both look like close code 1006, so the UI could not tell "log in again" from "reconnect". An upgrade that offers the `pulse` subprotocol with a missing or wrong token is therefore accepted and closed at once with **4401**, before anything is read. Other clients (Bearer) still get HTTP 401. The handshake, with its constants, is specified in `pulse_contracts::auth` and exported to TypeScript.
- **The daemon proves itself before any client sends it a credential** (added after a review found every client sending the token to whatever held the port). `GET /auth/proof?nonce=<32 to 128 hex digits>[&agent=<name>|&resume=true]` needs no credential and answers `{ instance, proof }`, `proof = hex(HMAC(HMAC(credential, "pulse/daemon-proof/v1"), port \0 instance \0 nonce))`, where the credential is the daemon token, that agent's MCP token, or this instance's resume code. `instance` is 16 random bytes drawn at each start. Clients pick the nonce, compare in constant time, and on a wrong answer send nothing and report "something else is listening on Pulse's port". The derived key is used for nothing else and every message starts with the port, so the endpoint is no oracle for any token or code, and a program on another port cannot relay a real daemon's answer. The Rust implementation is `pulse_daemon::auth::proof`; the web UI (WebCrypto) and the desktop shell (`node:crypto`) have their own, and all three test one vector, which an independent HMAC computation produced. The Rust client and the `pulse mcp` bridge send the proof request and then the credential on **one** HTTP/1.1 keep-alive connection (the client upgrades that connection to the WebSocket), so the answer and the token go to the same peer; browsers and the shell cannot, see the threat model. A client older than this, or a daemon older than this, does not talk to the other: an old daemon answers 404 and is reported as "something else" (the message says to stop it with the binary that started it). Pulse has had no release yet, so nothing in the field breaks.
- **How the browser gets the token** (0002 suggested the token in the URL fragment): `pulse open` puts a **login code** in the fragment (`#login=<code>`), and the UI exchanges it at `POST /auth/login` for the token. The code is `expiry.HMAC(secret, expiry)`, valid for two minutes and once. Which codes were spent is kept in memory only, so a daemon refuses codes minted before it started; before this, a spent code worked again for the rest of its two minutes after a restart. The UI drops the fragment (`history.replaceState`) before anything else runs.
  - `pulse open` first checks the daemon's proof (it will not send a browser to a port that cannot give one), then writes `$PULSE_HOME/open.html` (mode 0600, replaced atomically by each `pulse open`, so there is never more than one) that redirects to the `#login=` URL (`location.replace`, with a meta refresh and a link as fallbacks) and opens the **file's path** with `xdg-open` or, on macOS, `open`. Before this, the URL with the code was `xdg-open`'s argument, readable by every local user in `/proc/<pid>/cmdline`, and the reviewer showed a loop scanning `/proc` redeeming it before the browser did. The page stays in the home with a code that is spent or expired two minutes later; it is not deleted, because nothing tells `pulse open` when the browser has read it. `pulse open --print` (and `--json`) print the URL instead: to the user's own terminal or a pipe, which other users cannot read. Browsers packaged as snaps or flatpaks cannot read files in hidden directories such as `~/.pulse`; on Linux, when the page's path has a hidden component, `pulse open` says to use `--print` if the browser shows an error.
  - The UI keeps the token **in memory only**. A reload signs in again with a **resume code**: `r.<hex HMAC(HMAC(token, "pulse/ui-resume/v1"), instance)>`, which the page computes for the daemon instance that last proved itself, and writes to `sessionStorage` only on `pagehide` (removed again on `pageshow` from the back/forward cache). The next page load takes it out of storage before anything else, asks the daemon to prove it knows that resume code for that instance, and posts it to `POST /auth/login` as the code. The daemon accepts the resume code of its own instance only, as often as the tab reloads, so a daemon restart ends it (the tab needs `pulse open` if it reloads before it has reconnected; once reconnected it computes the new instance's code). Before this, the token sat in `sessionStorage`, where any page served on the daemon's origin could read it. Pages on `localhost` write no resume code (a browser can reach `[::1]` for it, which the daemon does not listen on).
  - A 4401 (the token was rotated) makes the UI drop its resume code and ask for `pulse open` instead of retrying. A failed proof is retried with backoff, since the real daemon may come back on its port, and shown for what it is.
- **Rotating the token** is `pulse stop`, delete `$PULSE_HOME/token`, `pulse start` (`load_or_create_token` makes a new one). It reaches every surface: windows get 4401 or a failed proof, login and resume codes and every agent token stop working (the `pulse mcp` bridge derives the new agent token from the file; HTTP MCP configurations need `pulse agents mcp-credentials` again). A command for it was not added: the three steps are what it would do, and deleting the file while the daemon runs changes nothing until it restarts.
- **Agent tokens** are `pa.<agent>.<hex HMAC-SHA256(secret, "pulse/agent-token/v1\0" + agent)>`: self-describing, so verification needs no lookup, and rotating the secret revokes all of them.
- The static UI is served without a token (it is the public app; it holds no data) but behind the Host check, with a Content-Security-Policy (`default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src 'self' ws://127.0.0.1:<port> ws://localhost:<port>; manifest-src 'self'; worker-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`; the built UI needs nothing inline: React sets styles through the CSSOM, which the policy allows, and Vite emits one script and one stylesheet), `X-Frame-Options: DENY` (it has approve buttons; for browsers without `frame-ancestors`), `nosniff`, `Referrer-Policy: no-referrer` and `Cross-Origin-Opener-Policy: same-origin`. The HTML page reads login codes from its address and is `no-store`; hashed `assets/` are cached for a year; the rest revalidates by ETag. Paths without an extension fall back to `index.html`. Without `apps/web/dist` at build time a placeholder page says how to build the UI (the same policy, with inline styles allowed). The real-daemon browser suite fails on any CSP violation.
- **RPC**: one request per frame (batches get `invalid_request`), up to 16 in flight per connection (responses may arrive out of order), 64 subscriptions per connection, 4 MiB frames. `system.shutdown` replies before shutting down.
- Nothing logs headers, queries or bodies, so tokens and event content stay out of the log.
- **Connections are bounded** (`pulse_daemon::server`, replacing `axum::serve`, which offered neither bound). Any local process can connect without a token, and with `axum::serve` one that sent half a request header held graceful shutdown, and so `daemon.lock`, forever: `pulse stop` hung and `pulse start` was refused (found in review). Now request headers must arrive within 30 s (also between requests on a keep-alive connection), at most 512 HTTP connections are served at once (more wait in the accept queue, so a flood cannot use up the file descriptors SQLite, sources and runs need), and shutdown drops whatever is still open 3 s after it began, with a warning in the log. Not bounded: a slow request body to `/auth/login`, which reads one without a token, and a local process that keeps all 512 slots busy; that denies the listener, not the engine, and loopback TCP says nothing about which local user is calling. Upgraded WebSockets do not count against the 512 (they carry the daemon token).

## Lifecycle

- **Shutdown is bounded except for runs.** Connections get 3 s (above); sources, the engine and the retention task end at once on cancellation; a calendar download in progress is abandoned, not awaited. The one wait left unbounded is the worker's, for each run's process group to be reaped: SIGTERM, the agent's grace period, SIGKILL, then the reap. A process stuck in uninterruptible sleep (a hung NFS mount) is not reaped until the kernel lets it go, and the daemon waits for it rather than leave a run it cannot account for.
- One daemon per Pulse home, by `flock` on `daemon.lock` (released by the OS however the process ends). `daemon.json` (`pulse_contracts::status::DaemonInfo`) is written after the listener is bound and removed on exit. `pulse stop` asks for shutdown, then waits on the lock, so it returns when the daemon has really exited (runs terminated, database checkpointed).
- `pulse start --detach` re-executes itself in a new process group with `--ready-line` and returns once the child prints `ready <port>`; before that, the child's stderr is shown if it fails. Config errors and warnings come first as `note <text>` lines, which the parent prints, so a detached start still tells the user what is wrong.
- Logs: `$PULSE_HOME/logs/pulse.log`, rotated at 10 MB, five old files kept. Retention runs at start and hourly, in batches of 500 with yields between.
- **Time is injected** (`Clock::System`, or `Clock::Tokio` which follows tokio's clock), so tests under `tokio::time::pause()` see a 10-minute debounce pass instantly.

## CLI

- `pulse ingest` decodes each stdin line as an `IngestEvent` itself and sends batches as soon as stdin has nothing more ready, so `tail -f log | pulse ingest -s ci` streams. `POST /ingest` uses `pulse_sources::ingest::parse` (objects, arrays, JSON lines). Both fill `causation_run` from `PULSE_RUN_ID`.
- `pulse run` forwards SIGINT, SIGTERM, SIGHUP and SIGQUIT to the command only until it has reaped it. After the reap it may still drain output for 200 ms (a background process can hold it), and a signal then is not forwarded: the command's ID, and its group's once the group is empty, may already name another process. A leftover in the command's group gets no signal then either; it is no longer ours to identify.
- `pulse run` reports through `events.report` with a 3 s bound and is silent when the daemon is unreachable; it exits with the command's code (128 + signal when killed, 127 when it cannot run the command).
- Exit codes: 0, 1 error, 2 usage, 3 the daemon is not running.
- **Definitions from the CLI** (0009): `pulse sources add <kind> <name> <path|url> [--cron|--every …]`, `pulse agents add --file`, `pulse rules add --file` (the bare table `rules show` prints and `test-rule --file` reads; `-` is stdin), and `… remove`. They call the same `*.upsert` / `*.delete` services as the UI, so write-back keeps comments, and they print the config warnings about what was added. Editing a definition in place stays the config file's or the UI's job.
- **Text output escapes terminal control.** Event content (file names, commit messages, agent output) reaches the terminal through `pulse events`, `tail`, `runs logs`; escape sequences in it could recolour or retitle the terminal or write the clipboard (OSC 52), bidi overrides misdisplay names, and tag characters carry text nobody sees. All text output goes through `print_line` / `eprint_line`, which print control and invisible formatting characters escaped (`\u{1b}`, `\u{e0041}`; the list is `pulse_core::prompt::is_invisible`, see 0003); `--json` is unchanged (JSON escapes control characters, and its readers are programs).

## Known limits

- `[daemon] mcp_events_extension` is read at start, like the port.
- Pending debounces are not persisted (0002, unchanged).
- Live `dropped` counts are a summary, not an exact count, when a subscriber lags the broadcast (see Fan-out).
